## 1. Basics

**Priority:** ⭐ must-know

**What it is:** MongoDB is a **document database**. Data is stored as JSON-like **documents** (in binary form, BSON) grouped into **collections**. Documents in one collection don't need identical fields.

**Why it exists:** Application code works with objects that have nested data: an order with its line items and shipping address. A relational database splits that into 3+ tables and joins them back on every read (the "object-relational impedance mismatch"). MongoDB stores the object as one document, so reading an order is a single lookup, and the schema can evolve without migrations for every new field.

**How it works**

| Relational | MongoDB |
|---|---|
| Database | Database |
| Table | Collection |
| Row | Document |
| Column | Field |
| Primary key | `_id` (always present, unique, immutable) |
| JOIN | Embedding, or `$lookup` |
| Foreign key | Reference (no enforcement) |

### 1.1 BSON

Binary JSON. Compared to JSON it:
- Adds types: `ObjectId`, `Date`, `Decimal128` (for money), `Int32`/`Int64`/`Double`, `BinData`, `Timestamp`, regular expressions.
- Stores lengths, so the database can skip over fields quickly.

Money gotcha: a JavaScript number is a double. Store prices as `Decimal128` or integer paise/cents, never as floating point.

### 1.2 `_id` and ObjectId

Every document has a unique `_id`. If you don't provide one, the driver generates an **ObjectId** (12 bytes):

```
| 4-byte timestamp (seconds) | 5-byte random value | 3-byte counter |
```
- Generated by the client, so no round trip or central counter is needed.
- Roughly **time-ordered**, so `ObjectId.getTimestamp()` gives creation time, and sorting by `_id` ≈ sorting by creation.
- Not a secret: it's guessable-ish and leaks creation time. Don't use it as an access token.

You can use your own `_id` (an email, a SKU, a UUID) when there's a natural unique key.

### 1.3 Limits worth knowing

- **16MB maximum document size**. (Store large files with GridFS or, better, in S3 with a reference.)
- **100 levels** of nesting.
- **64 indexes** per collection.

### 1.4 When to use MongoDB

✅ Good fit:
- Data that's naturally a self-contained document read and written as a unit: product catalogs with varying attributes, CMS content, user profiles with preferences, IoT device state, game state.
- Rapidly evolving schemas in early-stage products.
- Very large datasets needing built-in horizontal scaling (sharding).

❌ Poor fit:
- Highly relational data with many-to-many relationships and ad-hoc joins (accounting, ERP).
- Workloads that need many multi-document transactions (possible, but you're fighting the model).
- Heavy ad-hoc analytical reporting across entities.

### Interview Questions

**Q1. What is MongoDB and how is it different from a relational database?** ⭐
A document database storing BSON documents in collections. Instead of normalizing data across tables and joining, you usually store related data together in one document (embedding), which matches application objects and makes common reads a single lookup. Schemas are flexible per document, horizontal scaling (sharding) is built in, and single-document writes are atomic. Relational databases enforce schemas and relationships and excel at joins and multi-row transactions.

**Q2. What is BSON and why not plain JSON?** ⭐
Binary JSON: a binary encoding that supports more types than JSON (ObjectId, Date, Decimal128, 32/64-bit integers, binary data) and includes length prefixes, so it's faster to traverse and parse. JSON is text-only with a single number type.

**Q3. What's inside an ObjectId?** ⭐
12 bytes: a 4-byte Unix timestamp, a 5-byte random value unique to the machine/process, and a 3-byte incrementing counter. It's generated client-side without coordination, is unique in practice, and is roughly ordered by creation time.

**Q4. Is MongoDB schemaless?** ⭐
It's schema-flexible, not schemaless. The database doesn't require every document to look the same, but your application always assumes a shape. You can (and should) enforce a schema with `$jsonSchema` validation for important collections. Flexibility moves the responsibility for handling old document shapes to the application.

## 2. Schema Design

**Priority:** ⭐ must-know (the most important MongoDB topic in interviews)

**What it is:** Deciding what goes in one document, what gets its own collection, and how documents refer to each other.

**Why it matters:** In relational design you normalize first and think about queries later. In MongoDB, the rule is: **design for how the data is accessed.** "Data that is accessed together should be stored together." A schema that fights your queries makes MongoDB slow and complicated.

**How it works**

### 2.1 Embed vs reference ⭐

**Embedding:** put related data inside the parent document.
```javascript
// Order with embedded items and a snapshot of the address
{ _id: 501, userId: ..., items: [ {...}, {...} ], shippingAddress: {...} }
```

**Referencing:** store the other document's `_id` and look it up separately (or with `$lookup`).
```javascript
// Reviews reference the product
{ _id: ..., productId: 100, userId: ..., rating: 5, text: "..." }
```

| Embed when | Reference when |
|---|---|
| Data is read together (order + its items) | Data is read independently (product details vs its reviews) |
| The child belongs to one parent ("contains" relationship) | The child is shared by many parents (a product in many orders) |
| The child list is **small and bounded** (addresses, ≤ dozens) | The list is **large or unbounded** (comments, followers, log entries) |
| Data changes rarely, or you want a historical snapshot | Data changes often and must be the same everywhere (product price, user name) |
| You need atomic updates across parent + child (single-document atomicity) | The child is very large |

**Unbounded arrays are the classic mistake:** embedding all comments in a post, or all orders in a user, works at first, then documents grow toward 16MB, every update rewrites a huge document, and indexes on the array become enormous.

### 2.2 Modeling relationships

| Relationship | Typical approach | ShopKart example |
|---|---|---|
| **One-to-one** | Embed | User ↔ profile/preferences |
| **One-to-few** | Embed an array | User → addresses (a handful) |
| **One-to-many** | Reference from the child (child stores the parent's ID), or embed if bounded | Product → reviews (`reviews.productId`) |
| **One-to-squillions** | Always reference from the child | Device → millions of sensor readings |
| **Many-to-many** | Arrays of IDs on one or both sides, or a linking collection | Products ↔ categories (`categoryIds: [..]`) |

### 2.3 Design patterns ⭐⭐

**Extended reference:** copy the few frequently needed fields of the referenced document to avoid a lookup.
```javascript
// Order keeps a snapshot of product name and price (also historically correct)
items: [ { productId: 100, name: "Galaxy S26", unitPrice: 79999, qty: 1 } ]
```
Trade-off: duplicates must be updated if they must stay current. Choose fields that rarely change, or where the snapshot is the *right* value (price at purchase time).

**Subset:** embed only the most-used part of a large related set; keep the rest in a separate collection.
```javascript
// Product shows the 10 latest reviews on the page; the rest load on "See all"
{ _id: 100, name: "...", recentReviews: [ /* 10 latest */ ], reviewCount: 3412 }
```

**Computed:** precompute values on write instead of calculating on every read.
```javascript
{ _id: 100, ratingSum: 16800, ratingCount: 3412 }   // avg = sum / count, updated with $inc per review
```

**Bucket:** group many small time-series records into one document per time window.
```javascript
// One document per sensor per hour instead of one per reading
{ sensorId: "s1", hour: ISODate("2026-11-08T10:00Z"), count: 60,
  readings: [ { t: ..., v: 21.4 }, ... ], min: 20.9, max: 22.1, sum: 1290.3 }
```
Fewer documents, smaller indexes, pre-aggregated stats. (MongoDB 5.0+ **time series collections** do this automatically.)

**Attribute:** turn many similar, sparsely used fields into an array of key/value pairs so one index covers them.
```javascript
// Instead of { color: ..., ramGb: ..., screenIn: ..., size: ..., material: ... }
specs: [ { k: "color", v: "black" }, { k: "ramGb", v: 8 } ]
// one index: { "specs.k": 1, "specs.v": 1 }
```

**Outlier:** design for the typical case and handle rare huge cases separately.
```javascript
// A book usually has a few hundred buyers; a bestseller has millions
{ _id: "book1", buyers: [ /* up to 1000 */ ], hasOverflow: true }
// overflow buyers go into extra documents
```

**Polymorphic:** different shapes in one collection, distinguished by a type field.
```javascript
{ type: "mobile", name: "...", ramGb: 8 }
{ type: "shoe",   name: "...", size: 9, material: "leather" }
```

**Schema versioning:** add a `schemaVersion` field so the application can handle old and new shapes and migrate documents lazily (see §11).

**Tree patterns** (categories, org charts): parent reference (`parentId`), child references, **array of ancestors** (`ancestors: ["Electronics", "Mobiles"]` for fast "everything under Electronics" queries), or materialized paths (`path: ",Electronics,Mobiles,"`).

**Approximation:** update a counter only every Nth event when exact values don't matter (page views), reducing writes.

### 2.4 Anti-patterns

- **Unbounded arrays** (§2.1).
- **Massive number of collections** (e.g. one per user): each has indexes and files; overhead adds up.
- **Bloated documents:** loading a 2MB document to show a name in a list.
- **Over-normalization:** modeling MongoDB like SQL, with references everywhere and `$lookup` on every read.
- **Case-sensitive queries without a matching collation index**, leading to regex scans.

### Interview Questions

**Q1. When do you embed and when do you reference?** ⭐
Embed when data is accessed together, belongs to one parent, and is bounded in size (order items, user addresses), which gives single-read access and atomic updates. Reference when the related data is large or unbounded, shared across many documents, accessed independently, or changes frequently and must stay consistent (reviews, products in orders, comments). Mixed approaches like extended reference or subset are common.

**Q2. Why are unbounded arrays a problem?** ⭐
Documents keep growing toward the 16MB limit, every update rewrites a larger document (more I/O, more oplog and replication traffic), multikey indexes on the array grow huge, and reading the document fetches data you usually don't need. Use a separate collection referencing the parent, or the subset/bucket patterns.

**Q3. How would you model an e-commerce order in MongoDB?** ⭐⭐
One `orders` document containing embedded line items, each with product ID plus a snapshot of name and unit price (extended reference; the historical price is the correct value), the shipping address snapshot, status and status history, and payment summary. Products, users and reviews are separate collections. This makes "show order" one read and creating an order one atomic insert.

**Q4. What is the bucket pattern?** ⭐⭐
Grouping many small related records (sensor readings, events) into one document per time window or per N items, often with precomputed aggregates (count, min, max, sum). It cuts document count and index size dramatically and speeds up range reads. MongoDB's time series collections implement it automatically.

**Q5. How do you model a many-to-many relationship?** ⭐⭐
Store an array of references on the side with fewer links (e.g. `product.categoryIds`) and index it (multikey), optionally on both sides if queried both ways. If the relationship has its own attributes or is very large on both sides (students ↔ courses with grades), use a separate linking collection, like a junction table.

## 3. CRUD and Query Operators

**Priority:** ⭐ must-know

### 3.1 Create

```javascript
db.products.insertOne({ _id: 300, name: "Earbuds", price: 2999, stock: 100, tags: ["audio"] });
db.products.insertMany([ {...}, {...} ], { ordered: false });   // ordered:false → continue after errors
```

### 3.2 Read

```javascript
// SQL: SELECT name, price FROM products WHERE category = 'Mobiles' AND price < 50000 ORDER BY price DESC LIMIT 10
db.products.find(
  { category: "Mobiles", price: { $lt: 50000 } },     // filter
  { name: 1, price: 1, _id: 0 }                         // projection
).sort({ price: -1 }).limit(10);
```

**Operators:**

| Type | Operators |
|---|---|
| Comparison | `$eq`, `$ne`, `$gt`, `$gte`, `$lt`, `$lte`, `$in`, `$nin` |
| Logical | `$and`, `$or`, `$not`, `$nor` |
| Element | `$exists`, `$type` |
| Evaluation | `$regex`, `$expr` (compare fields), `$text`, `$mod` |
| Array | `$all`, `$elemMatch`, `$size` |

```javascript
db.orders.find({ $or: [ { status: "CANCELLED" }, { total: { $gt: 100000 } } ] });
db.products.find({ "attributes.brand": "Samsung" });              // dot notation into nested fields
db.products.find({ discountPrice: { $exists: true } });
db.orders.find({ $expr: { $gt: ["$total", "$creditLimit"] } });   // compare two fields of the same doc
```

### 3.3 Querying arrays ⭐

```javascript
db.products.find({ tags: "5g" });                          // array CONTAINS "5g"
db.products.find({ tags: { $all: ["5g", "android"] } });   // contains both
db.products.find({ tags: { $size: 2 } });                  // exactly 2 elements

// Orders containing product 100 with qty >= 2
// ❌ Wrong: conditions can match DIFFERENT array elements
db.orders.find({ "items.productId": 100, "items.qty": { $gte: 2 } });
//   matches an order with {productId:100, qty:1} and {productId:205, qty:3}

// ✅ $elemMatch: all conditions must hold for the SAME element
db.orders.find({ items: { $elemMatch: { productId: 100, qty: { $gte: 2 } } } });
```
That `$elemMatch` distinction is a favourite interview question.

### 3.4 Update

```javascript
db.products.updateOne(
  { _id: 100 },
  {
    $set:   { price: 74999, "attributes.ramGb": 12 },   // set fields (creates if missing)
    $unset: { discountPrice: "" },                       // remove a field
    $inc:   { stock: -1, soldCount: 1 },                 // atomic increment/decrement
    $currentDate: { updatedAt: true }
  }
);

// Array updates
db.users.updateOne({ _id: uid }, { $push: { addresses: { label: "office", ... } } });
db.products.updateOne({ _id: 100 }, { $addToSet: { tags: "bestseller" } });   // only if not present
db.products.updateOne({ _id: 100 }, { $pull: { tags: "old" } });             // remove matching
db.products.updateOne({ _id: 100 }, { $push: { recentReviews: { $each: [review], $sort: { at: -1 }, $slice: 10 } } });
                                                                               // keep only the 10 latest

// Update a matched array element with the positional operator $
db.orders.updateOne(
  { _id: 501, "items.productId": 205 },
  { $set: { "items.$.qty": 2 } }
);
// $[] = all elements, $[<id>] with arrayFilters = elements matching a condition
```

**Atomic stock decrement (prevents overselling):**
```javascript
const res = await db.products.updateOne(
  { _id: 100, stock: { $gte: 1 } },     // condition and update in one atomic operation
  { $inc: { stock: -1 } }
);
if (res.modifiedCount === 0) throw new Error("Out of stock");
```

`replaceOne` replaces the whole document (except `_id`). `findOneAndUpdate` returns the document before or after the update (`returnDocument: "after"`), useful for counters and queues.

### 3.5 Upsert

```javascript
// Add to cart: create the cart line, or increase qty if it exists
db.carts.updateOne(
  { userId: uid, productId: 100 },
  { $inc: { qty: 1 }, $setOnInsert: { addedAt: new Date() } },
  { upsert: true }
);
```
Under concurrency, two simultaneous upserts can both insert unless there's a **unique index** on the filter fields (`{ userId: 1, productId: 1 }`); with it, one fails with a duplicate key error and the driver/app retries it as an update.

### 3.6 Delete

```javascript
db.sessions.deleteMany({ expiresAt: { $lt: new Date() } });
db.products.deleteOne({ _id: 300 });
```

### 3.7 Bulk writes

```javascript
db.products.bulkWrite([
  { updateOne: { filter: { _id: 1 }, update: { $inc: { stock: -2 } } } },
  { insertOne: { document: { _id: 9, name: "New" } } },
  { deleteOne: { filter: { _id: 7 } } }
], { ordered: false });
```

### Interview Questions

**Q1. What does `$elemMatch` do and why is it needed?** ⭐
It requires all the given conditions to be satisfied by the **same** array element. Without it, `{ "items.productId": 100, "items.qty": { $gte: 2 } }` can match a document where one element has productId 100 and a different element has qty ≥ 2.

**Q2. How do you prevent overselling in MongoDB?** ⭐
Put the stock check in the update filter and decrement atomically: `updateOne({ _id, stock: { $gte: qty } }, { $inc: { stock: -qty } })`, then check `modifiedCount`. Single-document updates are atomic, so two concurrent buyers can't both succeed for the last unit. For multi-product orders, use a transaction or reserve each item and compensate on failure.

**Q3. `$push` vs `$addToSet`?** ⭐
`$push` always appends (duplicates allowed); `$addToSet` appends only if an equal value isn't already present. `$push` supports modifiers (`$each`, `$sort`, `$slice`, `$position`), e.g. to keep a capped list of the latest 10 items.

**Q4. How do you update one element inside an array?**
Use the positional `$` operator with a filter on the array (`"items.productId": 205` → `$set: { "items.$.qty": 2 }`) for the first match, `$[]` for all elements, or `$[elem]` with `arrayFilters` for all elements matching a condition.

## 4. Aggregation Pipeline

**Priority:** ⭐ must-know

**What it is:** MongoDB's framework for data processing and analytics. Documents flow through a sequence of **stages**, each transforming the stream, like a Unix pipe.

```
collection → [$match] → [$group] → [$sort] → [$limit] → results
```

### 4.1 Core stages and SQL equivalents

| Stage | Purpose | SQL equivalent |
|---|---|---|
| `$match` | Filter documents | `WHERE` / `HAVING` (after a `$group`) |
| `$project` / `$addFields` (`$set`) | Choose/compute fields | `SELECT` list |
| `$group` | Group and aggregate | `GROUP BY` + aggregates |
| `$sort` | Order | `ORDER BY` |
| `$limit` / `$skip` | Paginate | `LIMIT` / `OFFSET` |
| `$unwind` | One output document per array element | Like joining a parent to its child rows |
| `$lookup` | Join with another collection | `LEFT OUTER JOIN` |
| `$count` | Count documents | `COUNT(*)` |
| `$facet` | Several sub-pipelines on the same input | Several queries at once |
| `$bucket` / `$bucketAuto` | Group into ranges | `CASE` ranges + `GROUP BY` |
| `$setWindowFields` (5.0+) | Window functions | `OVER (PARTITION BY ... ORDER BY ...)` |
| `$unionWith` | Combine collections | `UNION ALL` |
| `$out` / `$merge` | Write results to a collection | `CREATE TABLE AS` / `MERGE` (materialized view) |

### 4.2 Example: revenue per category in November

```javascript
db.orders.aggregate([
  { $match: { status: { $ne: "CANCELLED" },
              createdAt: { $gte: ISODate("2026-11-01"), $lt: ISODate("2026-12-01") } } },
  { $unwind: "$items" },                                   // one doc per line item
  { $lookup: {                                             // join products for category
      from: "products", localField: "items.productId", foreignField: "_id", as: "product" } },
  { $unwind: "$product" },
  { $group: {
      _id: "$product.category",
      revenue: { $sum: { $multiply: ["$items.qty", "$items.unitPrice"] } },
      orders:  { $addToSet: "$_id" } } },
  { $project: { _id: 0, category: "$_id", revenue: 1, orderCount: { $size: "$orders" } } },
  { $sort: { revenue: -1 } }
]);
```
Equivalent SQL:
```sql
SELECT p.category, SUM(oi.qty * oi.unit_price) AS revenue, COUNT(DISTINCT o.id) AS order_count
FROM orders o JOIN order_items oi ON oi.order_id = o.id JOIN products p ON p.id = oi.product_id
WHERE o.status <> 'CANCELLED' AND o.created_at >= '2026-11-01' AND o.created_at < '2026-12-01'
GROUP BY p.category ORDER BY revenue DESC;
```

### 4.3 `$group` accumulators

`$sum`, `$avg`, `$min`, `$max`, `$first`, `$last`, `$push` (collect into an array), `$addToSet` (distinct values), `$count`, and (5.2+) `$top`, `$bottom`, `$topN`, `$firstN`, `$maxN`.

```javascript
// Top 3 most expensive products per category (5.2+)
{ $group: { _id: "$category", top3: { $topN: { n: 3, sortBy: { price: -1 }, output: { name: "$name", price: "$price" } } } } }
```

### 4.4 `$lookup` in depth

```javascript
// Simple equality join
{ $lookup: { from: "users", localField: "userId", foreignField: "_id", as: "user" } }

// Pipeline form: filter/limit the joined documents
{ $lookup: {
    from: "orders",
    let: { uid: "$_id" },
    pipeline: [
      { $match: { $expr: { $eq: ["$userId", "$$uid"] } } },
      { $sort: { createdAt: -1 } },
      { $limit: 3 }
    ],
    as: "recentOrders" } }
```
- Always an **outer** join (unmatched → empty array). Add `{ $match: { user: { $ne: [] } } }` for inner-join behaviour.
- **Index the `foreignField`**, otherwise each input document triggers a collection scan.
- Works with sharded `from` collections since 5.1.
- Frequent `$lookup` in hot paths is a sign the schema should embed or use extended references.

### 4.5 `$facet`: several results in one query

```javascript
// Product listing page: results + filter counts + total, in one round trip
db.products.aggregate([
  { $match: { category: "Mobiles" } },
  { $facet: {
      results:      [ { $sort: { price: 1 } }, { $skip: 0 }, { $limit: 20 } ],
      brandCounts:  [ { $group: { _id: "$attributes.brand", count: { $sum: 1 } } } ],
      priceRanges:  [ { $bucket: { groupBy: "$price", boundaries: [0, 10000, 30000, 60000, 200000],
                                   default: "other", output: { count: { $sum: 1 } } } } ],
      total:        [ { $count: "n" } ]
  } }
]);
```

### 4.6 `$setWindowFields` (window functions, 5.0+)

```javascript
// Running total of each user's spend and rank of each order by value
db.orders.aggregate([
  { $setWindowFields: {
      partitionBy: "$userId",
      sortBy: { createdAt: 1 },
      output: {
        runningTotal: { $sum: "$total", window: { documents: ["unbounded", "current"] } },
        movingAvg3:   { $avg: "$total", window: { documents: [-2, 0] } },
        orderRank:    { $rank: {} }
      } } }
]);
```

### 4.7 Performance rules ⭐⭐

1. **`$match` (and `$sort` + `$limit`) as early as possible**: only the first stages can use indexes. A `$match` after `$unwind` or `$group` scans everything.
2. **`$project` away unneeded fields early** to shrink documents flowing through the pipeline.
3. **`$sort` + `$limit` together** let MongoDB keep only the top N in memory (top-k sort).
4. **Memory limit:** each stage may use up to **100MB** of RAM. Beyond that it spills to disk (`allowDiskUse`, on by default since 6.0), which is slower.
5. **`$unwind` multiplies documents**: unwinding an array of 100 items turns 1 document into 100. Filter before unwinding.
6. **Index the `$lookup` foreign field.**
7. **Precompute** heavy, repeated aggregations into a summary collection with `$merge` on a schedule (a materialized view).
8. Check with `explain("executionStats")`.

The optimizer reorders some stages automatically (e.g. moves `$match` before `$project`), but don't rely on it.

### Interview Questions

**Q1. What is the aggregation pipeline?** ⭐
A sequence of stages that process documents in order, each stage's output feeding the next: filter (`$match`), reshape (`$project`), group (`$group`), sort, join (`$lookup`), unwind arrays, window functions and so on. It's MongoDB's equivalent of SQL's GROUP BY, joins and analytic queries, executed inside the database.

**Q2. How do you optimize an aggregation pipeline?** ⭐⭐
Filter and sort first so those stages can use indexes, project only needed fields, pair `$sort` with `$limit`, avoid unwinding large arrays before filtering, index lookup foreign fields, watch the 100MB per-stage memory limit, and precompute frequent heavy aggregations into collections with `$merge`. Verify with `explain`.

**Q3. How do you join collections in MongoDB? Is it a good idea?** ⭐
With `$lookup` in an aggregation (left outer join), using `localField/foreignField` or a sub-pipeline. It works, but if you need it on every hot read, the schema probably should embed or copy the needed fields (extended reference), because MongoDB is designed around reading self-contained documents.

**Q4. What does `$unwind` do?** ⭐
It deconstructs an array field, producing one document per element with the array replaced by that element. Used to group or filter by array elements (e.g. revenue per product across orders). Use `preserveNullAndEmptyArrays: true` to keep documents whose array is empty or missing.

**Q5. How do you do faceted search (results plus filter counts) in one query?** ⭐⭐
`$facet` runs several sub-pipelines on the same filtered input: one returns the paginated results, others compute counts per brand, price buckets and the total. Everything returns in one round trip. For large catalogs, Atlas Search's faceting is more efficient.

## 5. Indexing

**Priority:** ⭐ must-know

**What it is:** Same concept as in relational databases (file 01 §6): MongoDB indexes are **B-trees** (in WiredTiger), every collection has a unique index on `_id`, and without a suitable index a query does a **collection scan (COLLSCAN)**.

### 5.1 Index types

```javascript
// Single field
db.users.createIndex({ email: 1 }, { unique: true });

// Compound
db.orders.createIndex({ userId: 1, status: 1, createdAt: -1 });

// Multikey: automatically created when the field is an array (one entry per element)
db.products.createIndex({ tags: 1 });

// Text (basic full-text search; one per collection)
db.products.createIndex({ name: "text", description: "text" });
db.products.find({ $text: { $search: "wireless earbuds" } });

// Geospatial
db.stores.createIndex({ location: "2dsphere" });
db.stores.find({ location: { $near: { $geometry: { type: "Point", coordinates: [73.85, 18.52] }, $maxDistance: 3000 } } });

// TTL: delete documents automatically after a time
db.sessions.createIndex({ createdAt: 1 }, { expireAfterSeconds: 3600 });
db.otps.createIndex({ expiresAt: 1 }, { expireAfterSeconds: 0 });     // expire at the stored time

// Partial: index only matching documents
db.orders.createIndex({ createdAt: 1 }, { partialFilterExpression: { status: "PENDING" } });

// Unique among non-deleted users only
db.users.createIndex({ email: 1 }, { unique: true, partialFilterExpression: { deletedAt: { $exists: false } } });

// Sparse: skip documents missing the field (partial indexes are usually the better choice)
db.users.createIndex({ referralCode: 1 }, { sparse: true, unique: true });

// Wildcard (4.2+): index unknown/dynamic field names
db.products.createIndex({ "attributes.$**": 1 });

// Hashed: used for hashed sharding, equality only
db.users.createIndex({ _id: "hashed" });

// Case-insensitive via collation
db.users.createIndex({ name: 1 }, { collation: { locale: "en", strength: 2 } });
```

**TTL details:** a background task runs about every 60 seconds, so documents can live a little past their expiry. Always also check expiry in your query logic if precision matters (OTPs).

**Multikey limitation:** a compound index can include **at most one array field** per document (you can't index two arrays together because it would need every combination).

### 5.2 The ESR rule ⭐

For compound indexes, order fields as **E**quality → **S**ort → **R**ange.

```javascript
// Query: one user's orders with status SHIPPED, total > 1000, newest first
db.orders.find({ userId: uid, status: "SHIPPED", total: { $gt: 1000 } }).sort({ createdAt: -1 });

// ✅ ESR: equality (userId, status) → sort (createdAt) → range (total)
db.orders.createIndex({ userId: 1, status: 1, createdAt: -1, total: 1 });
```
Why: equality fields narrow the index to one contiguous section; within it, entries are already sorted by `createdAt`, so no in-memory sort is needed. If the range field came before the sort field, the matching entries would span several `total` values and need sorting.

**Sort direction:** for a compound sort, the index must match the directions exactly or exactly reversed. Index `{ a: 1, b: -1 }` supports `sort({ a: 1, b: -1 })` and `sort({ a: -1, b: 1 })`, but not `sort({ a: 1, b: 1 })`.

**Prefixes:** like SQL's leftmost-prefix rule, `{ userId: 1, status: 1, createdAt: -1 }` also serves queries on `userId` alone and `userId + status`.

### 5.3 Covered queries

If the filter and projection use only indexed fields (and `_id` is excluded unless indexed), MongoDB answers from the index alone:
```javascript
db.users.createIndex({ email: 1, name: 1 });
db.users.find({ email: "asha@x.com" }, { _id: 0, name: 1 });   // covered: totalDocsExamined = 0
```

### 5.4 `explain()` ⭐

```javascript
db.orders.find({ userId: uid, status: "SHIPPED" }).sort({ createdAt: -1 }).explain("executionStats");
```
What to check:

| Field | Healthy | Problem |
|---|---|---|
| `winningPlan.stage` | `IXSCAN` → `FETCH` | `COLLSCAN` (no index used) |
| `SORT` stage present? | No (index provides order) | In-memory sort |
| `totalKeysExamined` / `totalDocsExamined` vs `nReturned` | Close to each other | Examined ≫ returned → index not selective enough |
| `executionTimeMillis` | Low | High |

Rule of thumb: an ideal query examines about as many keys and documents as it returns.

### 5.5 Building indexes in production

Since 4.2, index builds hold an exclusive lock only briefly at start and end; reads and writes continue during the build. On a replica set the build runs on all members together (4.4+). Still, building a big index uses CPU and I/O, so do it off-peak. Atlas also offers rolling index builds.

Use `$indexStats` to find unused indexes, and hide an index (`db.coll.hideIndex()`) to test the impact of dropping it, like MySQL's invisible indexes.

### Interview Questions

**Q1. What is the ESR rule?** ⭐
Order compound index fields as Equality first, then Sort, then Range. Equality fields narrow to a contiguous index range, sort fields are then already ordered (no in-memory sort), and range fields filter last. Putting a range field before the sort field forces a blocking sort.

**Q2. What is a multikey index and what's its limitation?** ⭐⭐
An index on an array field; MongoDB creates one index entry per array element, so queries on any element can use it. A compound index can't contain more than one array field in the same document (it would need entries for every combination), and multikey indexes on big arrays get large.

**Q3. How do you tell if a query uses an index?** ⭐
`explain("executionStats")`: look for `IXSCAN` (index) vs `COLLSCAN` (collection scan) in the winning plan, check for a `SORT` stage (in-memory sort), and compare `totalKeysExamined` and `totalDocsExamined` with `nReturned`. The closer they are, the better the index.

**Q4. How do TTL indexes work? Are they exact?** ⭐⭐
A TTL index on a date field makes a background monitor delete documents once `field + expireAfterSeconds` has passed (or at the stored date when `expireAfterSeconds: 0`). The monitor runs about every 60 seconds and deletes in batches, so documents can outlive their expiry briefly. Don't rely on it for exact timing; check expiry in the query too.

**Q5. Sparse vs partial index?** ⭐⭐
A sparse index skips documents that don't have the field. A partial index uses an arbitrary filter expression (e.g. only `status: "PENDING"` or only non-deleted documents), so it's more flexible and is recommended over sparse. Both are smaller than full indexes; a query must include the partial filter condition for the planner to use a partial index.

## 6. Transactions and Consistency

**Priority:** ⭐⭐ commonly asked

### 6.1 Single-document atomicity

**Every write to a single document is atomic**, including updates to embedded arrays and subdocuments. This is why good MongoDB schema design keeps data that must change together in one document: no transaction needed.

```javascript
// Atomic: add item, update total and stock-check flag in one document
db.orders.updateOne({ _id: 501, status: "CART" },
  { $push: { items: newItem }, $inc: { total: newItem.unitPrice * newItem.qty } });
```

### 6.2 Multi-document transactions

Available since **4.0** (replica sets) and **4.2** (sharded clusters). ACID with **snapshot isolation**.

```javascript
const session = client.startSession();
try {
  await session.withTransaction(async () => {
    const res = await db.collection("products").updateOne(
      { _id: 100, stock: { $gte: 1 } }, { $inc: { stock: -1 } }, { session });
    if (res.modifiedCount === 0) throw new Error("Out of stock");     // aborts the transaction
    await db.collection("orders").insertOne({ _id: 501, userId, items: [...], status: "PLACED" }, { session });
  }, { readConcern: { level: "snapshot" }, writeConcern: { w: "majority" } });
} finally {
  await session.endSession();
}
```
`withTransaction` automatically retries on `TransientTransactionError` (e.g. write conflicts) and retries the commit on `UnknownTransactionCommitResult`.

**Costs and limits:**
- Default maximum runtime **60 seconds** (`transactionLifetimeLimitSeconds`).
- **Write conflicts:** if two transactions modify the same document, one gets a write conflict and must retry (MongoDB doesn't make it wait like a relational lock).
- Keep them small: MongoDB recommends modifying no more than about 1,000 documents per transaction.
- Slower than single-document writes, especially across shards (2PC between shards).
- Operations in a transaction hold WiredTiger cache pressure; long transactions hurt.

Guidance: **use transactions when you need them, but if you need them everywhere, reconsider the schema** (or the database).

### 6.3 Write concern ⭐⭐

How many replica set members must acknowledge a write before it's reported successful.

| writeConcern | Meaning | Risk |
|---|---|---|
| `{ w: 0 }` | Fire and forget, no acknowledgement | Errors and loss unnoticed |
| `{ w: 1 }` | Primary acknowledged | Lost if the primary fails before replicating (rolled back) |
| `{ w: "majority" }` | A majority of voting members have it (**default since 5.0**) | Survives failover |
| `{ j: true }` | Written to the on-disk **journal** before acknowledging | Survives a crash of that node |
| `{ wtimeout: 5000 }` | Give up waiting after 5s (the write may still succeed later!) | |

### 6.4 Read concern ⭐⭐

What data a read may return.

| readConcern | Returns | Use |
|---|---|---|
| `local` (default) | The node's latest data, which may be **rolled back** later | Most reads |
| `available` | Like local; on sharded clusters may return orphaned documents | Lowest latency |
| `majority` | Only data acknowledged by a majority (won't be rolled back) | Reads that drive important decisions |
| `linearizable` | Majority + guarantees it reflects all majority writes that completed before the read (primary only, slower) | Strongest single-document reads (e.g. a lock document) |
| `snapshot` | A consistent point-in-time view across documents | Transactions, consistent multi-document reads |

**Causal consistency:** with **causally consistent sessions** (`majority` read and write concerns), a client always reads its own writes and sees operations in causal order even when reading from secondaries.

### 6.5 Read preference

Which members a read may go to: `primary` (default), `primaryPreferred`, `secondary`, `secondaryPreferred`, `nearest`. Reading from secondaries scales reads and lowers latency for distant users, but the data may be **stale** (replication lag). Use it for analytics or "eventually consistent is fine" screens, not for read-after-write flows.

### Interview Questions

**Q1. Does MongoDB support ACID transactions?** ⭐
Yes. Every single-document operation is atomic, and since 4.0 (replica sets) / 4.2 (sharded clusters) MongoDB supports multi-document ACID transactions with snapshot isolation. They have overhead and limits (60s default lifetime, write conflicts cause retries), so the preferred design keeps data that changes together in one document.

**Q2. Explain write concern `w: 1` vs `w: majority`.** ⭐⭐
`w: 1` acknowledges once the primary has the write. If the primary fails before a secondary copies it, the new primary won't have it and the old primary rolls it back: an acknowledged write is lost. `w: majority` acknowledges only after a majority of voting members have it, so it survives failover. Majority is the default since 5.0; add `j: true` to require journal durability.

**Q3. What read concern would you use for a balance check?** ⭐⭐
At least `majority` (so you don't act on data that could be rolled back), read from the primary, and for the strongest guarantee on a single document, `linearizable`. Better still, do the check and the update in one atomic conditional update or inside a transaction with snapshot read concern.

**Q4. What happens if you read from a secondary right after writing?** ⭐⭐
You may not see your write, because replication is asynchronous. Fix it by reading from the primary for read-after-write flows, or by using causally consistent sessions with majority concerns, which make the secondary wait until it has caught up to your session's operation time.

## 7. Storage Engine

**Priority:** ⭐⭐⭐ senior / deep dive

**WiredTiger** has been the default storage engine since 3.2.

- **Document-level concurrency:** uses optimistic concurrency control with MVCC; two writers to *different* documents in the same collection don't block each other. Two writers to the **same** document conflict, and one retries.
- **MVCC and snapshots:** readers see a consistent snapshot; old versions kept in memory as long as needed.
- **Compression:** collections compressed with snappy by default (zstd and zlib available); indexes use prefix compression. Data on disk is often 2–5× smaller than raw JSON.
- **Cache:** WiredTiger's internal cache defaults to the **larger of 50% of (RAM − 1GB) or 256MB**. The rest of RAM is used by the OS file cache (holding compressed data). Your **working set** (frequently used data + indexes) should fit in the cache. When it doesn't, reads hit disk and latency jumps.
- **Durability:**
  - **Journal** (WAL): writes go to the journal, flushed every 100ms by default, or immediately with `j: true`.
  - **Checkpoints**: every 60 seconds, a consistent snapshot of data is written to disk. After a crash, MongoDB recovers from the last checkpoint and replays the journal.
- **B-tree** storage for both collections and indexes (WiredTiger also supports LSM, but MongoDB uses B-trees).

### Interview Questions

**Q1. What is WiredTiger and what concurrency does it provide?** ⭐⭐⭐
MongoDB's default storage engine. It provides document-level concurrency via MVCC and optimistic concurrency (conflicting writes to the same document retry), compression for data and indexes, an internal cache, and durability through a write-ahead journal plus periodic checkpoints.

**Q2. How much memory does MongoDB need?** ⭐⭐⭐
Enough for the working set (hot documents plus the indexes used by common queries) to fit in the WiredTiger cache, which defaults to about half of RAM minus 1GB. If the working set exceeds it, cache eviction and disk reads increase and latency suffers. Monitor cache usage, eviction activity and page faults.

## 8. Replication

**Priority:** ⭐⭐ commonly asked

**What it is:** A **replica set** is a group of `mongod` nodes holding the same data: one **primary** (accepts writes) and **secondaries** (replicate from the primary). Production minimum: **3 members**.

```
              writes / reads
App ──────────────────────────► PRIMARY ──oplog──► SECONDARY 1
                                    │
                                    └────oplog──► SECONDARY 2
          (heartbeats every 2s between all members)
```

### 8.1 The oplog

The **operations log** is a special capped collection (`local.oplog.rs`) on every member, recording every write as an **idempotent** operation:
```javascript
// You run:        db.products.updateOne({_id:100}, {$inc: {stock: -1}})   (stock was 10)
// Oplog records:  { op: "u", ns: "shop.products", o: { $set: { stock: 9 } }, o2: { _id: 100 } }
```
`$inc` is converted to `$set` of the resulting value, so replaying the entry twice is harmless.

Secondaries tail the oplog of their sync source and apply entries. The oplog is a fixed size: if a secondary is offline longer than the **oplog window** (time range the oplog covers), it can't catch up and needs a full **initial sync**. Size the oplog to cover maintenance windows (hours to days).

### 8.2 Elections

- Members exchange **heartbeats** every 2 seconds. If the primary isn't reachable for `electionTimeoutMillis` (10s default), an eligible secondary calls an election.
- The protocol is **Raft-like**: a candidate needs votes from a **majority** of voting members. The most up-to-date eligible node with the highest priority usually wins.
- During an election (typically a few seconds to ~12s) there's **no primary**, so writes fail. Drivers with **retryable writes** (on by default) retry once automatically after the new primary appears.
- Max 50 members, max **7 voting** members.

**Member types:**
- **Priority 0:** never becomes primary (e.g. a node in a remote DR data center).
- **Hidden:** priority 0, invisible to apps; used for backups or analytics.
- **Delayed:** applies the oplog with a delay (e.g. 1 hour), a safety net against accidental deletes.
- **Arbiter:** votes but holds no data. Cheap tie-breaker, but **discouraged**: in a Primary-Secondary-Arbiter set, if the secondary dies, writes with `w: majority` can't be acknowledged (only one data-bearing node).

### 8.3 Rollback

If a primary accepted writes that hadn't reached a majority, then stepped down, the new primary won't have them. When the old primary rejoins as a secondary, it **rolls back** those writes (saving them to rollback files for manual review). `w: "majority"` writes are never rolled back, which is why it's the default.

### Interview Questions

**Q1. How does MongoDB replication work?** ⭐⭐
A replica set has one primary that takes writes and records them in the oplog; secondaries continuously pull and apply oplog entries. Members heartbeat each other; if the primary is unreachable, a majority-based election promotes a secondary. Clients discover the topology automatically and redirect writes to the new primary.

**Q2. What is the oplog and why must entries be idempotent?** ⭐⭐
A capped collection holding an ordered log of every write on the primary, which secondaries replay. Entries are idempotent (e.g. `$inc` is stored as `$set` to the final value) so applying an entry more than once, which can happen during recovery or initial sync, gives the same result.

**Q3. Why does a replica set need at least 3 members?** ⭐⭐
Elections need a majority of votes. With 2 members, if one fails the survivor has only 50% and can't elect itself, so there's no primary. With 3 members, any 2 form a majority, tolerating one failure. Odd numbers avoid ties.

**Q4. When can MongoDB lose an acknowledged write?** ⭐⭐⭐
When the write concern is weaker than majority (e.g. `w: 1`): the primary acknowledges, then fails before any secondary replicates the write; a secondary becomes primary without it, and the old primary rolls the write back when it rejoins. Majority write concern prevents this.

## 9. Sharding

**Priority:** ⭐⭐ commonly asked

**What it is:** Distributing a collection's data across multiple **shards** (each a replica set) to scale beyond one machine's storage and write capacity.

### 9.1 Architecture

```
            App (driver)
                │
          ┌─────▼─────┐   ┌─────────────┐
          │  mongos   │◄──│ Config      │  metadata: which ranges live on which shard
          │ (router)  │   │ servers (RS)│
          └──┬────┬───┘   └─────────────┘
     ┌───────┘    └────────┐
┌────▼─────┐         ┌─────▼────┐
│ Shard A  │         │ Shard B  │   each shard is a replica set
│ (RS)     │         │ (RS)     │
└──────────┘         └──────────┘
```
- **mongos:** stateless query router. Apps connect to mongos, not to shards.
- **Config servers:** a replica set storing cluster metadata (shard key ranges → shards).
- **Shards:** replica sets holding subsets of the data.

### 9.2 Shard key and chunks

The **shard key** is a field (or fields) present in every document; it decides which shard a document lives on. Data is divided into contiguous key ranges called **chunks** (128MB default since 6.0). The **balancer** moves ranges between shards to keep data evenly distributed (since 7.0 it balances by data size per shard).

**Ranged sharding:** chunks are ranges of the key value. Good for range queries on the key; risky with monotonically increasing keys.
**Hashed sharding:** chunks are ranges of `hash(key)`. Even write distribution for monotonic keys; range queries on the key hit all shards.
**Zone sharding:** pin key ranges to specific shards, e.g. EU customers' data on EU shards (data residency).

### 9.3 Choosing a shard key ⭐

| Property | Why | Bad example | Better |
|---|---|---|---|
| **High cardinality** | Data can be split into many chunks | `country` (few values → few huge, unsplittable "jumbo" chunks) | `userId` |
| **Low frequency** (no value too common) | Avoid hot chunks | `status` (90% "DELIVERED") | `userId` |
| **Non-monotonic** | Spread inserts | `createdAt` or ObjectId alone (every insert → last chunk → one hot shard) | Hashed `_id`, or `{ userId: 1, createdAt: 1 }` |
| **Matches queries** | Queries go to one shard | Key not in common filters → every query broadcast | Key used in the main query filters |

**ShopKart:** shard `orders` on `{ userId: 1, createdAt: 1 }` (or hashed `userId`): a user's orders live together, "my orders" hits one shard, and writes spread across users.

### 9.4 Targeted vs scatter-gather queries ⭐

- **Targeted:** the query includes the shard key (or its prefix), so mongos routes it to the one shard (or few) holding it. Fast, scales linearly.
- **Scatter-gather (broadcast):** the query lacks the shard key, so mongos asks **every** shard and merges results. Fine for rare queries; a scalability killer for hot paths.

```javascript
db.orders.find({ userId: uid })                    // targeted
db.orders.find({ status: "PENDING" })              // scatter-gather to all shards
```

### 9.5 Changing a shard key

Historically immutable. Now:
- **4.2+:** you can update a document's shard key *value* (moves it between shards; needs a transaction or retryable write).
- **4.4+:** `refineCollectionShardKey` adds suffix fields to an existing key (e.g. `{ customerId }` → `{ customerId, orderId }`) to split jumbo chunks.
- **5.0+:** `reshardCollection` changes the key entirely online (copies all data; resource heavy).

Still: choose carefully, because resharding a large collection is expensive.

### 9.6 Other sharding concerns

- **Unique indexes** must include the shard key as a prefix (MongoDB can't check uniqueness across shards otherwise). `_id` uniqueness across shards is only guaranteed by the application unless `_id` is the shard key.
- **Jumbo chunks:** chunks that exceed the size but can't be split because all documents share one key value; caused by low-cardinality keys.
- **Orphaned documents:** leftovers from interrupted chunk migrations; cleaned automatically; reads with `available` read concern may see them.

### Interview Questions

**Q1. How does MongoDB sharding work?** ⭐⭐
A collection is split by a shard key into ranges (chunks) distributed across shards, each a replica set. Clients connect to mongos routers, which use metadata from the config servers to route queries to the right shards; a balancer migrates ranges to keep shards even. Queries containing the shard key are targeted to one shard; others are broadcast to all.

**Q2. How do you choose a good shard key?** ⭐
High cardinality, evenly distributed values (no hot values), not monotonically increasing (or hashed if it is), and present in the most frequent queries so they're targeted. Often a compound key like `{ tenantId, createdAt }` or a hashed user ID. A poor key leads to hot shards, jumbo chunks or scatter-gather queries, and changing it later is expensive.

**Q3. Why is a monotonically increasing shard key bad?** ⭐⭐
With ranged sharding, every new document has a higher key than all existing ones, so all inserts land in the last chunk on a single shard. That shard becomes a write hot spot while others sit idle, and the balancer constantly migrates chunks off it. Hash the key, or prefix it with a well-distributed field.

**Q4. What's the difference between hashed and ranged sharding?** ⭐⭐
Ranged sharding keeps adjacent key values together, which is efficient for range queries on the key but risks hot spots. Hashed sharding distributes by hash, giving even writes even for monotonic keys, but range queries on the key must hit every shard.

**Q5. What is a scatter-gather query and how do you avoid it?** ⭐⭐
A query without the shard key, which mongos must send to all shards and merge. It gets slower and more expensive as shards are added. Avoid it by choosing a shard key that appears in hot queries, or by maintaining a secondary lookup collection sharded by the other field.

## 10. Change Streams

**Priority:** ⭐⭐ commonly asked

**What it is:** A real-time feed of data changes (insert, update, replace, delete) on a collection, database or whole cluster, built on the oplog. Requires a replica set or sharded cluster.

```javascript
const pipeline = [ { $match: { operationType: { $in: ["insert", "update"] }, "fullDocument.status": "PAID" } } ];
const stream = db.collection("orders").watch(pipeline, { fullDocument: "updateLookup" });

for await (const change of stream) {
  await notifyWarehouse(change.fullDocument);
  await saveResumeToken(change._id);          // persist progress
}
```

- **Resume tokens:** each event has a token (`change._id`). Store it; after a crash, restart with `resumeAfter: token` to continue without missing events, as long as the token is still within the oplog window.
- **Pre- and post-images** (6.0+): get the document as it was before the change.
- **`fullDocument: "updateLookup"`** fetches the current full document for updates (it may reflect later changes too).
- Only **majority-committed** changes are emitted, so you never react to a change that gets rolled back.

**Uses:** syncing to Elasticsearch or a cache, triggering notifications/workflows, CDC into Kafka (the MongoDB Kafka connector / Debezium), real-time dashboards, audit logs.

**Change streams vs tailing the oplog directly:** change streams are the supported API: they handle sharded clusters, permissions, resumability, and don't expose internal oplog formats.

### Interview Questions

**Q1. What are change streams?** ⭐⭐
A supported API for subscribing to real-time changes on a collection, database or cluster, built on the oplog. Events can be filtered with aggregation stages, emit only majority-committed changes, and are resumable via resume tokens, which makes them good for CDC, cache/search sync and event-driven workflows.

**Q2. How do you make a change stream consumer reliable?** ⭐⭐
Persist the resume token after processing each event (or batch) and restart with `resumeAfter`/`startAfter` on failure; make processing idempotent because events may be redelivered after a restart; make sure the oplog window is long enough to cover downtime; and handle invalidate events (e.g. a dropped collection).

## 11. Operations and Security

**Priority:** ⭐⭐ commonly asked

### 11.1 Diagnosing slow queries

```javascript
// Database profiler: log operations slower than 100ms
db.setProfilingLevel(1, { slowms: 100 });
db.system.profile.find().sort({ ts: -1 }).limit(5);

// What's running now
db.currentOp({ active: true, secs_running: { $gt: 5 } });
db.killOp(opid);

// Index usage
db.orders.aggregate([ { $indexStats: {} } ]);

// Server health
db.serverStatus().wiredTiger.cache;
```
Slow operations are also logged in the `mongod` log by default (over `slowms`, 100ms). Atlas offers the Performance Advisor (suggests indexes) and Query Profiler.

### 11.2 Schema validation

```javascript
db.createCollection("orders", {
  validator: { $jsonSchema: {
    bsonType: "object",
    required: ["userId", "status", "total", "items"],
    properties: {
      status: { enum: ["PLACED", "PAID", "SHIPPED", "DELIVERED", "CANCELLED"] },
      total:  { bsonType: "decimal", minimum: 0 },
      items:  { bsonType: "array", minItems: 1 }
    } } },
  validationLevel: "moderate",     // strict = all writes; moderate = skip existing invalid docs
  validationAction: "error"        // or "warn" (log only)
});
```

### 11.3 Schema migrations

With no `ALTER TABLE`, schema changes are handled by:
1. **Lazy migration:** the app reads both old and new shapes (using `schemaVersion`) and upgrades a document whenever it writes it.
2. **Background batch migration:** a script updates documents in batches (`updateMany` with a version filter), throttled to protect the cluster.
3. Usually both: deploy code that handles both shapes → run the batch migration → remove old-shape handling.

Tools: `migrate-mongo`, Mongoose plugins, or custom scripts.

### 11.4 Security

- **Enable authentication** (it's off by default in a bare install). Thousands of open MongoDB instances were wiped and held for ransom in the 2017 "MongoDB apocalypse".
- **Role-based access control:** built-in roles (`read`, `readWrite`, `dbAdmin`) and custom roles; least privilege.
- **Network:** bind to private interfaces (`bindIp`), firewall, VPC peering / private endpoints.
- **TLS** in transit; encryption at rest (WiredTiger encrypted storage in Enterprise/Atlas).
- **Client-side field-level encryption** and **Queryable Encryption** (7.0+): sensitive fields encrypted by the driver, so the server never sees plaintext, while still supporting equality (and, in 8.0, range) queries on them.
- **Auditing** (Enterprise/Atlas).

### 11.5 NoSQL injection ⭐⭐

```javascript
// ❌ Login endpoint passes JSON body straight into the query
app.post("/login", async (req, res) => {
  const user = await db.users.findOne({ email: req.body.email, password: req.body.password });
});
// Attacker sends: { "email": "admin@shop.com", "password": { "$ne": null } }
// → finds admin because password "is not null" → logged in without the password
```
**Prevention:**
- **Validate types:** ensure `email` and `password` are strings (Joi/Zod/class-validator schemas), or cast with `String()`.
- Use a sanitizer (`express-mongo-sanitize`) that strips keys starting with `$` or containing `.`.
- Mongoose with strict schemas casts values to the declared types (`strictQuery`).
- Never pass user input into `$where`, `$function` or `$accumulator` (they execute JavaScript); disable server-side JS if unused.
- And of course, compare password **hashes** (bcrypt), never plaintext.

### 11.6 Backups

`mongodump`/`mongorestore` (logical, slow for big data), filesystem/cloud snapshots, Atlas continuous backup with point-in-time restore, or Ops Manager. For sharded clusters, backups must be coordinated across shards and config servers (managed tools handle this).

### Interview Questions

**Q1. How do you find slow queries in MongoDB?** ⭐⭐
Enable the profiler (level 1 with a `slowms` threshold) or read slow-operation entries in the mongod log, inspect running operations with `currentOp`, then run `explain("executionStats")` on the offenders to check for COLLSCANs, in-memory sorts and examined ≫ returned. Atlas Performance Advisor suggests indexes automatically.

**Q2. What is NoSQL injection and how do you prevent it?** ⭐⭐
Passing untrusted JSON into a query so attackers can inject operators, e.g. `{ "$ne": null }` as a password to bypass login, or `$where` to run JavaScript. Prevent it by validating input types and shapes, sanitizing `$` and `.` keys, using ODM schemas that cast types, and avoiding server-side JavaScript operators.

**Q3. How do you handle schema changes in MongoDB?** ⭐⭐
Add a schema version field, deploy code that can read both old and new shapes, migrate documents lazily on write and/or with throttled background batches, then remove legacy handling. Use `$jsonSchema` validation (with `validationLevel: "moderate"` during transitions) to enforce the new shape for new writes.

## 12. Other NoSQL Types

**Priority:** ⭐⭐ commonly asked (awareness level)

### 12.1 Wide-column: Apache Cassandra (and ScyllaDB)

**Model:** tables with a **partition key** (decides which node stores the row) and **clustering columns** (sort order within the partition).
```sql
-- CQL: messages of a conversation, newest first
CREATE TABLE messages (
  conversation_id UUID,
  message_id TIMEUUID,
  sender_id UUID,
  body TEXT,
  PRIMARY KEY ((conversation_id), message_id)     -- partition key, clustering column
) WITH CLUSTERING ORDER BY (message_id DESC);
```
- **Query-first design:** you design a table **per query**. No joins, limited filtering (queries must specify the partition key), so data is heavily duplicated across tables.
- **Masterless, leaderless:** every node is equal; data placed with consistent hashing; replication factor (e.g. 3) per keyspace.
- **Tunable consistency** per query: `ONE`, `QUORUM`, `ALL`, `LOCAL_QUORUM`.
- **LSM-tree storage**: extremely fast writes.
- Watch out for: **large partitions** (bucket by time: `PRIMARY KEY ((conversation_id, month), message_id)`), **tombstones** (deletes are markers; many deletes slow reads), no ad-hoc queries.
- Real life: Discord (messages, later ScyllaDB), Netflix (viewing history), Apple, Uber.

### 12.2 Key-value: Amazon DynamoDB

- **Primary key:** a **partition key**, or partition key + **sort key**. All access is by key; `Query` reads items within one partition (optionally a sort-key range); `Scan` reads everything (avoid).
- **Secondary indexes:** **GSI** (Global Secondary Index: different partition key, eventually consistent, its own throughput) and **LSI** (Local: same partition key, different sort key, must be created with the table).
- **Single-table design:** store several entity types in one table with generic keys (`PK = USER#42`, `SK = ORDER#2026-11-01#501`) so one `Query` fetches a user and their orders together.
- **Capacity:** on-demand or provisioned RCU/WCU; **hot partitions** get throttled, so the key must spread load.
- Reads: eventually consistent by default, strongly consistent optionally (2× the cost). Transactions via `TransactWriteItems`.
- **DynamoDB Streams** for CDC; **TTL** attribute for expiry.
- Real life: Amazon's cart and order pipelines; any serverless backend on AWS.

### 12.3 Graph: Neo4j

- **Model:** nodes (with labels and properties) and relationships (typed, directed, with properties).
- **Strength:** traversals ("friends of friends who bought X") follow direct pointers between nodes ("index-free adjacency"), so cost depends on the part of the graph you touch, not total data size. The same query in SQL needs many self-joins that slow down with depth.
```cypher
// People Asha's friends follow that Asha doesn't already follow (recommendations)
MATCH (a:User {name: "Asha"})-[:FOLLOWS]->(:User)-[:FOLLOWS]->(rec:User)
WHERE NOT (a)-[:FOLLOWS]->(rec) AND rec <> a
RETURN rec.name, COUNT(*) AS mutuals ORDER BY mutuals DESC LIMIT 10;
```
- Real life: social networks, fraud rings (accounts sharing devices/cards), recommendation engines, knowledge graphs, network/IT dependency maps.

### 12.4 Search: Elasticsearch / OpenSearch

- **Inverted index:** term → list of documents containing it (with positions and frequencies).
- **Text analysis:** tokenizing, lowercasing, stemming ("running" → "run"), synonyms, n-grams for autocomplete.
- **Relevance scoring** (BM25), fuzzy matching (typos), facets/aggregations, highlighting.
- **Near-real-time:** a newly indexed document becomes searchable after a refresh (~1s by default).
- **Not a primary database:** no ACID transactions, weaker durability guarantees historically, and mappings are hard to change. Keep the source of truth in PostgreSQL/MongoDB and **sync** to Elasticsearch via CDC or events, then rebuild the index from the source when needed.
- Real life: product search on e-commerce sites, log analytics (ELK stack).

### Interview Questions

**Q1. When would you choose Cassandra over MongoDB?** ⭐⭐
For massive, write-heavy workloads with predictable query patterns that need multi-datacenter availability and linear horizontal scaling: chat messages, activity feeds, IoT, time-series. Cassandra's leaderless LSM design gives excellent write throughput and no single primary, but you must design a table per query and live without joins or ad-hoc queries. MongoDB is more flexible for querying and secondary indexes and is easier for general application data.

**Q2. What is single-table design in DynamoDB?** ⭐⭐⭐
Storing multiple entity types in one table with overloaded generic keys (e.g. `PK = USER#42`, `SK = PROFILE` or `ORDER#<date>#<id>`), so related items share a partition and can be fetched with a single Query. It's driven by the fact that DynamoDB has no joins and charges per request. It requires knowing access patterns upfront.

**Q3. Why use a graph database instead of SQL for social networks?** ⭐⭐
Queries like friends-of-friends or shortest paths need repeated self-joins in SQL, which get dramatically slower with each level. Graph databases store relationships as direct links, so traversals cost proportional to the neighbourhood explored, and query languages like Cypher express path patterns naturally.

**Q4. Why shouldn't Elasticsearch be your primary database?** ⭐⭐
It's optimized for search, not for being a system of record: no multi-document transactions, eventual visibility after refresh, mapping changes require reindexing, and historically weaker durability guarantees. Keep the source of truth in a transactional database and sync to Elasticsearch, so you can always rebuild the index.

## 13. MongoDB vs PostgreSQL JSONB

**Priority:** ⭐ must-know (a very common follow-up question)

| Area | MongoDB | PostgreSQL + JSONB |
|---|---|---|
| Data model | Documents everywhere | Relational tables + JSONB columns where needed |
| Schema | Flexible by default, optional `$jsonSchema` | Strict columns + flexible JSONB |
| Joins | `$lookup` (works, not its strength) | Native, efficient joins |
| Transactions | Single-doc atomic; multi-doc since 4.0 with overhead | Full ACID, mature, any number of rows |
| Constraints | Unique indexes, validation; no foreign keys | FKs, CHECK, exclusion constraints, triggers |
| Updating part of a document | Efficient in-place operators (`$set`, `$inc`, `$push`) | `jsonb_set`, but the whole JSONB value is rewritten (new row version) |
| Indexing JSON | Any field, multikey arrays, wildcard, compound | GIN (containment/existence), B-tree on expressions |
| Horizontal scaling | Built-in sharding, auto-balancing | Needs Citus or application sharding |
| High availability | Built-in replica sets with automatic failover | Needs Patroni or a managed service |
| Query language | MQL + aggregation pipeline | SQL (+ JSON path) |
| Analytics | Aggregation pipeline | Full SQL, window functions, mature BI tool support |
| Ecosystem | Document-first drivers/ODMs (Mongoose), Atlas Search/Vector Search | Huge SQL ecosystem, extensions (PostGIS, pgvector) |

**How to answer "MongoDB or PostgreSQL?":**
- **PostgreSQL (with JSONB)** if the data is mostly relational with some flexible attributes, you need strong integrity and multi-entity transactions (orders, payments, inventory), or ad-hoc reporting. It covers most document use cases well.
- **MongoDB** if the domain is genuinely document-shaped (catalogs, content, profiles, event payloads), documents are read/written as units, the schema evolves quickly, and you expect to need horizontal scale with built-in sharding and failover.
- Many companies use both: PostgreSQL for transactional core data, MongoDB for catalog/content.

### Interview Questions

**Q1. If PostgreSQL has JSONB, why would anyone use MongoDB?** ⭐
MongoDB is document-native: efficient partial updates of nested fields, flexible indexing on any nested/array field, built-in sharding and automatic failover, and a document-oriented developer experience. PostgreSQL JSONB is great for some flexible fields inside a relational model, but each JSONB update rewrites the whole value and scaling out needs extra tooling. The choice depends on whether the domain is primarily relational or primarily documents.

**Q2. Your team stores orders in MongoDB and now needs complex financial reports with joins. What would you do?** ⭐⭐
Don't force complex relational reporting onto the operational database. Stream changes (change streams/CDC) into a warehouse or a relational reporting database, model the data for reporting there, and run SQL. If transactional integrity across orders, payments and inventory is becoming painful too, that's a signal to reconsider PostgreSQL for that part of the system.
